# Kaisensei Deep Mode Spec

**目标：** 为 kaisensei 的 Deep Mode 建立一份可直接实施的产品与交互规格，覆盖入口、课程流、返回行为、课程数据、生成规则和恢复规则。

**范围：** 只定义 Deep Mode。Quick Mode 保持现有行为，不在本 spec 中重新设计。

---

## 1. 产品定位

Deep Mode 是独立于 Quick Mode 的深度课程模式。

Quick Mode 解决：

> 拍一张照片，快速生成一组短练习。

Deep Mode 解决：

> 基于一张真实照片，生成一套围绕真实场景的文字版口语训练，让用户逐步学会观察、理解、互动，并最终完成一段完整场景对话。

Deep Mode 前期只支持文字交互，不做语音输入，但所有内容都按真实口语表达设计。

Deep Mode 与 Quick Mode 的课程结构、生成协议、页面流程和数据结构完全分离。二者只共享拍照、上传和图片输入能力。

---

## 2. 已确认的关键决策

- 相机页已经预留 `深度` 开关。
- 用户在相机页选择 `深度` 后点击拍照，进入 Deep Mode 课程流程。
- 用户在相机页选择 `快速` 后点击拍照，进入 Quick Mode 课程流程。
- 用户在相机页选择 `深度` 后点击上传图片，也进入 Deep Mode 课程流程。
- 一旦进入课程，当前模式不可切换。
- 课程内不显示 `快速 / 深度` 模式标签或提示。
- 如果用户想换模式，必须返回相机页并重新拍照或重新上传。
- 课程内点返回，先回到上一个课程页面。
- 课程首页 / 纵览页点返回，回到相机页。
- 课程内返回时需要确认，避免误退出。

---

## 3. 架构边界原则

Deep Mode 和 Quick Mode 必须在代码层保持强隔离。

### 3.1 设计目标

这套边界不是临时整理，而是为未来把 Deep Mode 拆成独立项目预留条件。

### 3.2 允许共享的部分

只允许共享最小必要入口能力：

- 应用壳层
- 相机页的模式选择入口
- 图片拍摄 / 上传能力
- 路由跳转壳
- 最底层的通用 UI 基元，如按钮、卡片、图标、基础布局 token

### 3.3 不允许共享的部分

以下内容必须按模式隔离：

- 页面流
- 状态管理
- 课程数据结构
- 生成协议
- 题目判定逻辑
- 课程页面组件
- 课程导航逻辑
- 恢复 / 进度逻辑
- 模式专属文案

### 3.4 实施要求

- Deep Mode 不从 Quick Mode 页面组件里反向拼装
- Quick Mode 不引用 Deep Mode 的课程实现
- 公共组件只能做“无业务语义”的基础层
- 如果某段逻辑未来只属于 Deep Mode，就不要为了短期省事放进共享层
- 如果需要复用，优先复制薄壳式入口，再逐步抽离共享基元，而不是共享整棵组件树

### 3.5 拆分预期

后续如果把 Deep Mode 单独拆成独立项目，理想状态是：

- 只保留相机入口的最小共享壳
- Deep Mode 的课程页、状态、生成器和校验器可以整体迁出
- 不需要重写课程结构
- 不需要重做题目数据协议

### 3.6 具体落地原则

这份隔离不是只靠“目录分开”，而是要同时满足：

- 入口分开
- 状态分开
- 组件分开
- 数据协议分开
- 业务逻辑分开
- 依赖方向分开

任何一层只要继续把 Quick Mode 和 Deep Mode 交叉耦合，后面拆分都会变贵。

### 3.7 依赖方向

必须采用单向依赖：

```text
app shell
  ├─ quick mode
  └─ deep mode
```

规则：

- `app shell` 可以知道当前选了哪个模式
- `app shell` 可以把图片和基础入口参数交给对应模式
- `quick mode` 不能反向依赖 `deep mode`
- `deep mode` 不能反向依赖 `quick mode`
- 两边都只能依赖公共的无业务语义基础层

### 3.8 共享层边界

允许共享的只放“不会决定产品行为”的东西：

- 按钮、卡片、弹层、进度条、图标这类纯 UI 基元
- 颜色、间距、字号、圆角这类 design tokens
- 通用文本格式化、时间格式化、图片压缩、通用媒体工具

禁止放进共享层的东西：

- 模式选择逻辑
- 课程页路由
- 任何 lesson / course 状态机
- 任何练习判定规则
- 任何课程专属文案
- 任何 Deep Mode 专属生成协议

### 3.9 目录级建议

后续代码目录建议按下面思路拆，不要求一次性完全到位，但方向要按这个收敛：

```text
prototype/src/
  app/
    App.jsx
    app-shell.jsx
  shared/
    ui/
    utils/
    media/
  quick/
    quick-entry.jsx
    quick-camera.jsx
    quick-lesson/
    quick-api/
  deep/
    deep-entry.jsx
    deep-camera-entry.jsx
    deep-overview/
    deep-course/
    deep-api/
    deep-state/
```

要求：

- `app/` 只做模式分发和最外层壳
- `quick/` 放 Quick Mode 全部业务
- `deep/` 放 Deep Mode 全部业务
- `shared/` 只放不带模式语义的通用层

### 3.10 独立 entry 组件

Quick Mode 和 Deep Mode 都必须有自己的 entry 组件。

要求：

- `quick` 负责自己的入口壳
- `deep` 负责自己的入口壳
- `app shell` 只负责把模式路由到对应 entry
- entry 组件里可以接收相机输入、图片输入和基础上下文
- entry 组件之外不要再把两种模式混成同一套页面树

### 3.11 独立存储命名空间

Deep Mode 必须使用自己独立的存储 key 命名空间。

要求：

- 不复用 Quick Mode 的本地存储 key
- 不共用进度恢复 key
- 不共用草稿 key
- 不共用题目状态 key
- 如果未来拆成独立项目，Deep Mode 的数据读取方式不需要先清洗 Quick Mode 的历史键

### 3.12 独立文案命名空间

Deep Mode 必须有自己独立的模式文案。

要求：

- 相机页模式提示使用 Deep Mode 自己的文案
- 课程内返回确认使用 Deep Mode 自己的文案
- 加载、错误、完成、继续等 Deep Mode 专属文案不要从 Quick Mode 复用
- 可以复用通用语气，但文本内容由 Deep Mode 自己维护

### 3.13 第一阶段边界

Deep Mode 落地的第一阶段只做项目结构拆分和隔离基础，不改 Quick Mode 的既有学习逻辑。

第一阶段目标：

- 把 Quick Mode 和 Deep Mode 放进独立目录域
- 让 app shell 只负责模式分发
- 让共享层只保留无业务语义的基础能力
- 为后续 Deep Mode 独立实现课程流预留入口和状态边界

第一阶段非目标：

- 不重做 Quick Mode 的课程内容
- 不改 Build / Use 的现有判定
- 不推进 Deep Mode 课程题型实现
- 不把 Deep Mode 的课程页面和 Quick Mode 组件继续耦合在一起

### 3.10 迁移策略

为了不伤 Quick Mode，改造顺序要遵守：

1. 先把 Deep Mode 作为独立 feature 域搭起来
2. 再让入口壳把模式分发给对应 feature
3. 再把共享的纯 UI 基元慢慢抽到 `shared/`
4. 最后才考虑更进一步拆出独立项目

迁移期间禁止做的事：

- 一边重构一边把 Quick 和 Deep 的业务逻辑揉成公共大文件
- 为了省事把 Deep Mode 直接塞进 Quick Mode 现有组件树里
- 让 `App.jsx` 继续承担所有模式、页面和状态细节

## 4. 总体流程

```text
相机页
↓
选择 快速 / 深度
↓
拍照或上传
↓
加载 / 生成
↓
课程纵览页
↓
Notice
↓
Interpret
↓
Interact
↓
Step In
↓
课程完成
```

Deep Mode 进入后不再切回 Quick Mode。用户要换模式，只能回到相机页重新选择并重新输入图片。

---

## 5. 相机页规则

### 4.1 页面职责

相机页只负责两件事：

- 选择模式
- 输入图片

### 4.2 模式选择

- 默认展示 `快速 / 深度` 切换
- 模式只在输入图片前有效
- 模式切换影响下一次拍照或上传进入哪条课程流

### 4.3 图片输入

相机页支持：

- 拍照
- 上传图片

只要当前模式是 `深度`，无论是拍照还是上传，都会进入 Deep Mode。

### 4.4 进入课程

当用户完成拍照或上传后：

- 如果当前模式是 `深度`，生成 Deep Mode 课程
- 如果当前模式是 `快速`，保持现有 Quick Mode 流程

---

## 6. 课程纵览页

### 5.1 页面目标

课程纵览页只做一件事：

> 让用户快速理解这张照片被识别成了什么场景，并点击进入课程。

### 5.2 页面结构

纵览页顶部：

- 返回按钮
- 页面标题或品牌名
- 不显示模式切换
- 不显示模式标签

纵览页中间只展示一个可点击的引导卡片。

引导卡片分上下两部分。

#### 上半部分

- 展示用户拍摄或上传的照片
- 使用照片原图裁切
- 图片为卡片主视觉

#### 下半部分

固定三行：

1. 照片关键词，英文显示
2. 场景描述，中文显示
3. 固定引导语

示例：

```text
coffee · table · laptop
咖啡厅里悠闲的下午茶时间
点击开始这次学习之旅
```

要求：

- 关键词由 AI 识别照片中的客观内容
- 默认 3 个关键词
- 使用高频、具体、可见的名词
- 不加入推测内容
- 场景描述可以做合理、保守的情境推测
- 不要编造具体人物关系或无法判断的事实

### 5.3 交互

点击整张引导卡片后：

- 当前纵览页保持在左侧
- Notice 页面从右侧快速滑入
- 进入沉浸式学习流程
- 后续模块之间都使用横向滑入过渡
- 不回到纵览页作为默认学习路径

---

## 7. 学习页通用布局

Notice、Interpret、Interact、Step In 使用统一页面骨架。

### 6.1 顶部区域

左侧：

- 返回按钮
- 返回时弹出确认

中间：

- 四段主进度条
- 对应 Notice、Interpret、Interact、Step In
- 当前模块高亮
- 已完成模块使用完成色
- 未开始模块使用弱色

右侧：

- 用户照片的正方形缩略图
- 点击可放大查看原图
- 关闭后回到当前练习，不改变进度

### 6.2 模块内次级进度

在主进度条下方显示模块内部进度，例如：

```text
Notice · 4 / 14
```

模块内部进度按实际题目数量计算，不固定写死。

### 6.3 中间内容区

主要展示当前内容卡片、问题、候选词块和用户已选择内容。

每个页面只聚焦一个任务，不同时展示多组题目。

### 6.4 底部操作区

固定在页面底部：

- 清空或重置
- 提示
- 验证

验证按钮只有在用户完成必要选择后才可用。

## 8. Notice 模块

### 7.1 训练目标

训练观察型表达：

> 用户学习如何描述照片中真实可见的内容。

表达内容必须客观，不加入推测。

可覆盖：

- 物品
- 人物
- 动作
- 位置
- 空间关系
- 环境细节

### 7.2 内容结构

Notice 由以下部分组成：

```text
基础例句训练
↓
变式例句训练
↓
Quick Response
↓
Notice 里程碑
```

每个核心表达对应：

- 1 条基础例句
- 若干条变式例句
- 每条例句都经过同一组三步练习

默认：

- 2 个核心表达
- 每个核心表达 1 条基础例句
- 每个核心表达 1 条变式例句
- 2 道 Quick Response

数量必须可配置。

### 7.3 三步练习

每条基础例句和变式例句都依次经过：

```text
Understand → Focus → Build
```

#### Understand

目标：

> 先理解英文例句的自然中文含义。

页面内容：

- 上方内容卡片展示英文例句
- 当前核心表达使用强调色
- 下方展示若干自然分词的中文词块
- 可加入 1 个无用中文干扰词块

用户操作：

- 点击中文词块
- 按顺序组成自然中文句子
- 点击验证

#### Focus

目标：

> 在完整英文句子中识别并补全核心表达。

页面内容：

- 展示当前英文例句
- 设置 2 至 3 个空格
- 空格必须覆盖当前核心表达
- 下方展示英文候选词
- 可加入 1 个干扰词

#### Build

目标：

> 根据中文意思，重新拼出完整英文句子。

页面内容：

- 上方展示一句中文含义
- 中间为用户答案区域
- 下方展示自然切分的英文词块
- 可加入 1 个英文干扰词块

切分原则：

- 按自然词组和固定搭配切分
- 核心表达尽量保持为一个词块
- 不按单词机械切碎
- 不与 Understand 的中文切分强行一一对应

### 7.4 变式例句

基础例句完成后，进入同一核心表达的变式例句。

变式例句要求：

- 保留同一个核心表达
- 更换句子结构或表达角度
- 仍围绕当前照片场景
- 可以做轻度合理发散
- 不得跳到无关主题

### 7.5 Quick Response

所有基础例句和变式例句完成后，进入 Quick Response。

Quick Response 不是对话流，而是单轮问答。

页面结构：

- 上方显示一个与照片相关的问题
- 中间为用户答案区
- 下方为英文词组候选区
- 可加入 1 个干扰词组
- 用户通过词组重排生成答案

要求：

- 每道题对应一个核心表达
- 问题必须自然
- 答案必须复用对应核心表达
- 不要求用户自由输入
- 每题单独验证
- 完成后自动进入下一题

### 7.6 Notice 里程碑页

Notice 全部完成后，显示里程碑页。

内容：

- 模块名：Notice
- 完成提示
- 本模块学到的核心表达
- 一句能力总结

主按钮：

```text
Continue to Interpret
```

## 9. Interpret 模块

### 8.1 训练目标

训练推测型表达：

> 用户根据照片推测正在发生什么、人物状态、场景氛围或可能原因。

### 8.2 内容结构

Interpret 与 Notice 完全复用同一套页面和练习交互：

```text
基础例句
→ Understand
→ Focus
→ Build
→ 变式例句
→ Quick Response
→ 里程碑
```

### 8.3 生成要求

Interpret 的核心表达可以围绕：

- It looks like...
- It seems like...
- Maybe...
- They might be...
- This place feels...
- Someone may be...

基础例句要求：

- 必须是合理推测，不是虚构事实
- 推测要能够从照片线索中得到支持
- 可以描述行为、状态、氛围或原因
- 避免绝对断言

Quick Response 问题可包括：

- What might be happening here?
- How does this place feel?
- Why might someone choose this seat?

### 8.4 里程碑页

内容：

- 模块名：Interpret
- 已完成的核心表达
- 一句能力总结

主按钮：

```text
Continue to Interact
```

---

## 10. Interact 模块

### 9.1 训练目标

训练任务型互动：

> 用户在真实场景中表达需求，并在对方回复后自然回应。

Interact 合并原来的 Need、Say 和 Handle。

### 9.2 Task Pack

Interact 不按普通表达列表组织，而是按 Task Pack 组织。

每个 Task Pack 包含：

- 一个真实任务
- 一个 Need 核心表达
- 一个 Handle 核心表达
- Need 例句与变式
- Handle 例句与变式
- Dialogue Practice

默认：

- 2 个 Task Pack
- 每个 Task Pack 1 个 Need 核心表达
- 每个 Task Pack 1 个 Handle 核心表达
- Need 和 Handle 各 1 条基础例句
- Need 和 Handle 各 1 条变式例句
- 每个 Task Pack 1 轮 Dialogue Practice

### 9.3 Need / Handle 训练

Need 和 Handle 的基础例句与变式例句，仍复用 Notice / Interpret 的三步交互：

```text
Understand → Focus → Build
```

要求：

#### Need

- 必须表达清晰具体的真实需求
- 与照片场景高度相关
- 适合用户主动开口
- 优先使用礼貌、自然、高频表达

#### Handle

- 必须对应对方可能给出的真实回应
- 可以是接受、拒绝或条件式回应
- 用户回复要自然、简短、礼貌
- 不能脱离 Need 单独生成

### 9.4 Dialogue Practice

Interact 的 Dialogue Practice 使用同页面连续对话流。

推荐流程：

```text
系统给出场景
↓
用户完成 Need
↓
系统生成对方回复
↓
用户完成 Handle
```

要求：

- Need 和 Handle 必须属于同一个 Task Pack
- 对方回复必须与 Need 自然对应
- 对话保持短小，不追加额外轮次

### 9.5 里程碑页

内容：

- 模块名：Interact
- 已完成的真实任务
- 学到的 Need 表达
- 学到的 Handle 表达
- 一句能力总结

主按钮：

```text
Continue to Step In
```

## 11. Step In 模块

### 10.1 训练目标

Step In 是最终挑战。

> 用户综合使用 Notice、Interpret、Interact 中学到的表达，完成一段完整真实场景对话。

### 10.2 内容抽取规则

系统从已完成课程中抽取：

- 1 个 Notice 核心表达
- 1 个 Interpret 核心表达
- 1 个 Need 核心表达
- 1 个 Handle 核心表达

组合成一个完整互动任务。

不能重新引入新的核心表达。

### 10.3 页面形式

Step In 完全使用 Dialogue Practice 对话流界面。

区别是对话更完整，顺序更长：

```text
系统给出场景
↓
用户用 Notice 表达描述眼前情况
↓
系统回应或追问
↓
用户用 Interpret 表达做出判断
↓
系统给出互动机会
↓
用户用 Need 表达提出需求
↓
系统回复
↓
用户用 Handle 表达自然回应
```

所有用户输入仍使用词组重排，不做自由输入。

### 10.4 完成反馈

完成 Step In 后，显示课程完成页。

内容：

- 用户照片
- 完成提示
- 四个阶段的核心表达摘要
- 用户最终完成的完整对话
- 再次练习按钮
- 返回拍照页按钮

---

## 12. 课程导航和返回

- 课程内返回按钮必须先弹确认
- 课程首页 / 纵览页返回按钮直接回到相机页
- 课程内的返回只回上一级页面，不直接跳到相机页
- 如果用户想更换模式，必须回到相机页重新选择并重新输入图片

---

## 13. 课程状态与恢复

Deep Mode 课程较长，必须支持退出后恢复。

MVP 阶段只要求同设备同浏览器可恢复。先把恢复状态做成浏览器侧持久化，后续如果切到服务端恢复，优先复用同一组状态字段。

Deep Mode 的恢复状态必须写入独立命名空间，不得与 Quick Mode 混用。

至少保存：

```json
{
  "lessonId": "deep_xxx",
  "currentModule": "notice",
  "currentItemId": "notice_expression_1_base_focus",
  "completedItemIds": [],
  "attemptsByItemId": {},
  "usedHintsByItemId": {},
  "completedModules": [],
  "isCompleted": false
}
```

产品规则：

- 返回拍照页前弹出退出确认
- 退出后课程数据和当前进度保留
- 再次打开该课程时从上次题目继续
- 已完成题目默认不要求重做
- 已完成模块可以回顾，但回顾不改变主进度

---

## 14. 课程生成协议

### 13.1 输入结构

Deep Mode 课程生成器接受以下输入：

```json
{
  "mode": "deep",
  "level": "normal",
  "imageContext": "<image or image description>",
  "config": {}
}
```

### 13.2 输出结构

输出必须是完整 Deep Mode 课程 JSON，至少包含：

- `mode`
- `level`
- `overview`
- `modules.notice`
- `modules.interpret`
- `modules.interact`
- `modules.stepIn`

### 13.3 生成方式

MVP 默认采用一次 LLM 调用生成整套 Deep Mode 课程，然后由系统做确定性校验。

不采用固定多次拆分生成：

- 不单独识图再拼课程
- 不默认按模块拆成四次生成

这样做的原因：

- Notice、Interpret、Interact 和 Step In 之间关联强
- Step In 必须复用前面模块的表达
- 一次生成更容易保持场景、语气和任务一致

### 13.4 校验和重试

系统校验失败时：

- 不把不完整数据交给前端
- 使用同一照片、level 和 config 自动重新生成
- 重试仍失败时显示明确的生成失败状态

---

## 15. 内容和答案规则

- 所有内容必须围绕用户真实照片
- Notice 只能描述客观可见内容
- Interpret 只能做有照片依据的合理推测
- Interact 必须生成现实中可能发生的任务
- Step In 只能复用前面已经学习过的表达
- 不生成通用主题课
- 不列出大量孤立单词
- 不写长篇语法解释
- 不使用幼稚表达
- 不使用考试式长难句
- 所有题目都必须能通过结构化答案判定
- 不依赖 LLM 实时评分

---

## 16. 失败和降级

### 15.1 结构错误

出现以下情况视为生成失败：

- JSON 无法解析
- 缺少关键模块
- 数量与 config 不一致
- answer 无法由 chunks 组成
- Step In 引入大量新表达
- Notice 明显包含无依据推测
- Interact 与照片场景无关

处理：

- 不把不完整数据交给前端
- 自动重新生成
- 仍失败时显示明确生成失败状态
- 用户可重新生成或返回拍照页

### 15.2 照片信息不足

如果照片过暗、模糊、遮挡严重或没有足够可识别场景：

- 不要强行编造完整课程
- 返回可识别失败状态
- 提示用户重新拍摄或上传更清楚的照片

---

## 17. 验收标准

1. 相机页选 `深度` 后拍照，进入 Deep Mode。
2. 相机页选 `深度` 后上传图片，也进入 Deep Mode。
3. 相机页选 `快速` 后拍照，进入 Quick Mode。
4. 进入 Deep Mode 课程后看不到模式切换。
5. 课程内无法把 Deep Mode 切回 Quick Mode。
6. 想更换模式时，用户必须返回拍照页重新选择。
7. 课程内返回需要确认。
8. 课程首页返回会回到相机页。
9. Deep Mode 走完 Notice → Interpret → Interact → Step In。
10. 课程纵览页不显示模式标签，只显示课程内容。
11. Deep Mode 支持同设备同浏览器恢复进度。
12. Quick Mode 的已有行为不因 Deep Mode 改动而变化。
13. Deep Mode 的代码目录、状态和课程实现可在未来整体迁出为独立项目。
